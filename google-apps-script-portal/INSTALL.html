Attendance Learning Hub: Google edition install guide

For the school owner of the Google Workspace account. Works offline. All pictures are illustrative diagrams drawn for this guide, not screenshots. All names and values in them are placeholders.

Status: not deployed. No live records have been migrated. Not approved for cutover. This is a separate Google Apps Script application backed by private Google Sheets and Drive. It does not replace or read the running portal. Keep the existing portal running throughout testing.
Staff sign in with their existing school username through the existing staff account source. Learners choose Learner and use the separately supplied learner source. There is no public sign-up.

Use a school-owned Google Workspace account, not a personal account. Obtain school approval for the requested Sheets, Drive and external-request scopes before authorising them.

1Create the Google project

Open script.google.com, create a new project and name it Attendance Learning Hub - TEST.

2Add every exported file

Extract the supplied ZIP (attendance-google-apps-script.zip). From its apps-script folder, add every .gs file as a Script file and every .html file as an HTML file, keeping the names without extensions. This includes the generated Schema.gs and the bundled Bcrypt.gs, not only the files from the repository's src folder.

3Show and set the manifest

In Project Settings, enable Show "appsscript.json" manifest file in editor. Replace its contents with the supplied appsscript.json. The timezone is Europe/London.

4Private Script Properties

In Project Settings, open Script Properties. Start with MODE = TEST. Generate SESSION_KEY yourself: at least 32 cryptographically random characters from a trusted password manager or, for example, openssl rand -base64 32. Enter it only in Script Properties. Never put identifiers, password sources or secrets in HTML, instructions, chat, source control, workbooks or screenshots. No real key is provided.

IMPORT_APPROVALLeave unset; APPROVED_TEST_COPY approves a private TEST copy only
A plaintext password column is not a compatible hash. Do not copy it into the master workbook or replace it automatically.

5Initialise the test workbook

With MODE=TEST and SESSION_KEY set, select initializePortal_ in the editor function menu and press Run. Review the scopes before approving. It creates a new private workbook and upload folder and records their IDs. It refuses an existing unmarked workbook and never overwrites school tabs. Then run inspectPortal_. Keep the workbook and folder owner-only; do not change permissions on existing login workbooks.

6Sync accounts

Load only authorised synthetic test records, using the dry-run import process in README.md. Staff must exist in the staff directory; learners need an exact PersonCode match to a Students record. Run syncAccounts_ from the editor to create verified account mappings. This is not public registration.

7Assign course and tutor access explicitly

  • CourseAccess: verified username plus course ID.
  • DepartmentCourses: verified department plus course ID.
  • LearnerAssignments: student, account and tutor IDs.

A staff display name on a timetable never grants access. A learner needs confirmedLearner=true and a matching learner assignment to open termly reviews.

8Create a private test deployment

Deploy, New deployment, type Web app. Execute as the school-owned deployment account. Prefer access restricted to the school domain where policy allows. Google's restriction supplements, not replaces, the application login and record checks. Share the web-app link with testers, never a spreadsheet link.

9Acceptance before cutover

  1. Run ACCEPTANCE.md against the Google deployment and record actual results: dates across daylight-saving changes, role denial, two browsers editing the same register, and a simulated service failure. A local preview is not a pass.
  2. Only after separate approval: complete a security and capacity review, reconcile an approved transfer and agree a cutover time.
  3. Do not disable or delete the original portal or its data during testing. Never let both systems accept independent live writes without a reviewed reconciliation.
Reminder: this guide installs a TEST copy only. Nothing is deployed and no live records are migrated by following it.
